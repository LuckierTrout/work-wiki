## Intent

**Problem:** Four holes left by the two mount changes that keep surfaces alive behind `hidden`. (DW-422) `PreviewColumn` publishes `SurfaceVisibilityProvider` for the dialogs beneath it but nothing in the column itself reads the withdrawal, so a `dataVersion` bump during a Settings visit still refetches the row, still nudges the watcher through `requestDataVersionCheck()`, and still writes sentences into a polite region that `hidden` has taken out of the accessibility tree — the announcement is spent with nobody to hear it and the column the owner comes back to has changed under them with no report. (DW-519) `SourcesTree`'s scroll-memory effect is byte-for-byte the pre-DW-208 shape — the cleanup cancels the pending frame without flushing it — and `Workbench` renders the component as `mode === "sources" && …` inside a `settingsOpen ? null : …` branch, so it genuinely unmounts on a mode switch and on opening Settings and that cleanup really runs; no suite mounts it, so deleting the effect outright would leave the suite green. (DW-520) `.wb-preview` and `.wb-preview-body` are both `overflow: auto` and `.wb-preview[hidden] { display: none }` discards their scroll boxes for exactly the visit DW-416 fixes for the canvas, with no ref and no restore — two of the three surfaces that visit withdraws come back where the owner left them and the third does not. (DW-522) `withdrawn()`'s `getClientRects()` route is non-empty for a `visibility: hidden` element, and `globals.css`'s narrow block hides the closed rail exactly that way, so the predicate's docblock claims more than it covers.

**Approach:** Make the withdrawal a term in the rules the column already executes rather than a fact only its dialogs are told: `previewFetchPlan` gains a `visible` input that answers "do nothing" while the surface is off screen and leaves `shown` untouched, so returning is one silent refresh of the row the owner left; the nudge and the live region take the same gate, with a nudge raised while withdrawn deferred and flushed once on return. Give the Preview's two scroll boxes the DW-416 ref-and-restore keyed on `hidden`. Mirror `TreePanel`'s event-time capture and flushing cleanup into `SourcesTree` and mount it in a suite for the first time. And widen `withdrawn()` with `Element.checkVisibility` behind a capability test, shimmed in `vitest.setup.dom.ts` the way `getClientRects` already is, plus an `[inert]` ancestor route.

## Boundaries & Constraints

**Always:** The withdrawal is ONE fact with ONE spelling per surface — the `hidden` prop the component already receives, which is the same boolean its `SurfaceVisibilityProvider` publishes; nothing derives it a second way. Every rule a node suite can execute stays in a pure module: `previewFetchPlan` decides whether a run may fetch, and the component types no `hidden &&` beside it. A withdrawn surface never writes an offset read from a `display: none` box, and never loses one captured while it was showing. Preview scroll memory lives in a REF and dies with the tab, exactly as DW-416's canvas offset does. `withdrawn()` stays ONE predicate used by both restore arms, and both call sites keep the spelling `create-wiki-ui.test.ts:113-141` pins.

**Block If:** `Element.checkVisibility` cannot be shimmed in `vitest.setup.dom.ts` without changing what `getClientRects` or `offsetParent` answer for nodes the existing dialog suites restore focus to — that would mean the widened predicate disables restores the suite pins, and the mechanism needs rethinking rather than forcing.

**Never:** Do not call `Element.checkVisibility` unguarded — jsdom 30 ships no implementation, so a bare call is a `TypeError` that takes every dialog suite down. Do not add a `getComputedStyle` or an `offsetParent` check (jsdom applies no stylesheets and reports `null` for every element; either would disable every restore the suite pins). Do not invent a localStorage key for the Preview's offsets and do not claim FR-8 cross-session restore for them. Do not cancel, abort or reset anything the owner is holding when the surface goes off screen — no closing the editor, no dropping the draft, no aborting an in-flight save or revert; withdrawing is not closing. Do not band-key the Sources offset or change `readStoredSourcesScroll`/`writeStoredSourcesScroll`'s signatures. Do not touch `.wb-preview`'s or `.wb-sources-tree`'s CSS. Do not edit the deferred-work ledger.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| `dataVersion` bumps while the Preview is withdrawn | Settings open, column `hidden`, provider payload bumped | No request is issued, no sentence reaches the live region, and the row the column last read stays recorded | Nothing is reset; the payload, the editor and the draft are untouched |
| Settings closes over that bump | The same column comes back on screen | Exactly one silent refresh of the SAME row — `reset: false`, so `Loading…` never flashes — and its outcome announces normally | An unreachable refresh leaves the last-good bytes, as it does on screen |
| A save settles while the column is withdrawn | `save()` reaches its landed or unconfirmed branch with `hidden` true | The watcher nudge is HELD, not dropped, and fires once when the column comes back | A second write while still withdrawn collapses into the same single nudge |
| First render already withdrawn | Column mounts with `hidden` true and a selection | No read at all; the first read happens when it comes on screen, and it is a full reset because no row was ever recorded | `loading` stays true, which is what it means |
| Preview scrolled, then Settings visited | `.wb-preview` and `.wb-preview-body` scrolled, column withdrawn and restored | The SAME nodes come back at the same two offsets, and a scroll after the visit replaces them | A body branch not rendered on return restores nothing and starts at the top |
| Sources scrolled in the frame before the mode switch | `scroll` fires, the mode changes before the rAF runs | The captured offset is written for Sources in the cleanup, then restored on the next visit | A cleanup with no pending write flushes nothing |
| Dialog closes, opener under `visibility: hidden` | Opener `isConnected`, no `[hidden]` ancestor, non-empty client rects | No `focus()` on the opener; the fallback is judged by the same predicate | No error expected |
| `checkVisibility` absent from the platform | An engine that does not implement it | The predicate falls back to the attribute and rect routes it already had — never throws, never answers "withdrawn" for everything | No error expected |

**Acceptance Criteria:**
- Given a surface that goes off screen while holding owner state, when it is withdrawn, then nothing it holds is closed, reset or aborted — the withdrawal only stops work that nobody could observe.
- Given the Preview column comes back on screen after any withdrawal, when the effect re-runs, then the owner is told what changed by exactly one refresh of the row they left, not by a sentence spoken while they were away.
- Given a scrollable surface this shell withdraws with `display: none`, when it returns, then the same node is back at the offset it was scrolled to, from memory that dies with the tab.
- Given a scroll recorded in the last frame before a surface unmounts, when the cleanup runs, then the offset captured while the surface was showing is what storage holds — never a `scrollTop` read from a `display: none` box, and never nothing.
- Given a node hidden by any of the four routes the shell can produce, when a dialog closes onto it, then focus is refused and the fallback is judged by the same predicate — and on a platform without `checkVisibility` the predicate still answers, never throws.

## Design Notes

`previewFetchPlan`'s withdrawn outcome returns the UNCHANGED `shown` on purpose, and that is the whole of the resume behaviour:

```ts
if (!input.visible) return { fetch: false, reset: false, shown: input.shown };
if (!isSameSelection(input.shown, input.next)) return { fetch: true, reset: true, shown: input.next };
```

A run while withdrawn records nothing, so the row the column last read is still the recorded one when the column comes back — `isSameSelection` then answers `true` and the return is `{ fetch: true, reset: false }`: one silent refresh, no `Loading…` flash, no discarded draft. Had the withdrawn branch advanced `shown`, the return would have looked like the same row that was never actually read.

The nudge is DEFERRED rather than dropped because it is about the other readers, not this column: a save that settles mid-visit really did bump the kernel's tail, and the trees are withdrawn too. One pending flag collapses any number of writes into the single check the return needs.

DW-422's ModeCanvas half is coverage, not a rewrite. Every canvas `ModeCanvas` renders takes `active={mode === X && !hidden}` and guards its read with `if (!active) return;` over `[active, load, dataVersion]` — which IS "gate while withdrawn, one refresh on return", and is the precedent `PreviewColumn` is being brought up to. The two canvases without an `active` prop issue no unprompted read: `SearchCanvas` fetches only from its form, and `ChatCanvas`'s list and Skills scan are `[]`-keyed mount reads. What was missing is that nothing executes the property, so it could be undone silently.

DW-519 is scoped to the flush and the coverage. The band split DW-206 needed for the tree does not apply here: `.wb-tree-body` is capped at `40vh` below 900px, which gives it a second, shorter scroll range, while `.wb-sources-tree` has no narrow cap and sits in a `.wb-left` that is `overflow: visible` at that width — so at narrow widths it does not scroll, fires no `scroll` event, and writes nothing over the wide offset.
