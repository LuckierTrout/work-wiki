## Intent

**Problem:** `GET /api/settings` serves `objectVersion(await loadConfig())` — a hash computed over `firecrawlApiKey`, `customApiKey` and `embeddingApiKey` — four lines below the comment asserting no secret material crosses that boundary (AD-23), and `loadConfig()` answers `{}` for an UNREADABLE config as well as an absent one, so a transient storage error lets the `PUT` merge a patch into `{}` and write away every stored field. Two smaller edges ride along: `stableSerialize` collapses `Date`/`Map`/`Set`/class instances to `{}` and blows the stack on a cycle, and `isWorkbenchSettingsPayload` requires `version`, so an absent one would turn a landed save into a reported failure and take the whole canvas off screen.

**Approach:** Replace the content-derived settings version with an OPAQUE TOKEN generated on each successful `saveConfig` and stored in a sibling file beside the config, served as the precondition and compared on `PUT`. Teach the config loader to answer `absent` and `unreadable` differently so the route can refuse rather than merge. Harden `stableSerialize` and re-document `objectVersion` as a general primitive that is no longer the settings scheme. Make `version` optional on the workbench payload, matching `isPreviewPayload`/`useSettings`.

## Boundaries & Constraints

**Always:**
- The settings precondition token is generated by `saveConfig` and is derived from NOTHING in the config — no field, secret or not, contributes to it.
- The token file is written BEFORE the config file. A half-completed save must leave a token nobody holds (next save refused, recoverable) rather than a token that still matches a superseded config (silent lost update).
- `loadConfig()` keeps its exact current signature and `{}`-on-failure contract; ~50 call sites must not change. The new discriminated read is an ADDITIONAL export.
- An UNREADABLE config refuses on both `GET` and `PUT` with the same status and sentence, before any merge.
- A store with a config but no token file reports one fixed sentinel version, so a first save through the API can still land.
- Copy lives in a module constant, never typed at a render or route site.

**Block If:** the storage layer cannot distinguish "not found" from "failed" for the token file (it can — both backends throw `code: "ENOENT"`, see `src/lib/storage/r2.ts:354` and `src/lib/storage/filesystem.ts:98`).

**Never:**
- Do not put the token inside `AppConfig` / `.llm-wiki-config.json`. It is not a setting, it must not reach `getWorkbenchSettings`, `getEffectiveSettings`, backups or exports as one, and the config's stored shape stays exactly the fields it has today.
- Do not delete `objectVersion`/`stableSerialize`; they stay exported and get hardened.
- Do not widen the read-only switch, the owner gate, or the 412/428 vocabulary.
- Do not touch `loadConfigSync`'s cold-cache `{}` behaviour.

## Design Notes

**Why a sibling file, not a config field.** The token must not become a pseudo-setting: `AppConfig` is spread into `getWorkbenchSettings`, exported in backups, and compared field-by-field in the suite. `.llm-wiki-config.version` keeps the config's stored shape byte-identical to today.

**Write order is the safety property.**

```ts
export async function saveConfig(config: AppConfig): Promise<string> {
  const version = newConfigVersion();
  await getStorage().writeFile(configVersionRelPath(), version + "\n"); // FIRST
  await getStorage().writeFile(configRelPath(), JSON.stringify(config, null, 2) + "\n");
  _configCache = { data: { ...config }, ts: Date.now() };
  return version;
}
```

If the second write fails, the served version no longer matches any open draft: every surface is refused and recovers by reloading. The reverse order would leave a stale token matching a config that had already changed — the exact lost update the guard exists to catch.

**The sentinel's residual, stated honestly.** While a store is unstamped, two hand-edits of the config are indistinguishable to the guard. Every save through the API stamps a real token, so the window is the first save only, and hand edits never went through the guard anyway. Record this in the `saveConfig`/`UNSTAMPED_CONFIG_VERSION` docblocks rather than pretending it is closed.

### Residual risks

- **Out-of-band edits are invisible to the guard.** A change to `.llm-wiki-config.json` that does not go through `saveConfig` leaves the token untouched, so a draft seeded before it saves over it. This is inherent to the token scheme DW-198's recorded decision chose and is documented at `UNSTAMPED_CONFIG_VERSION`; the content-derived version did catch it, and that is the coverage traded for getting the three keys off the boundary.
- **A no-op save rotates the token,** so the other Settings surface is answered 412 for a change nobody made. Documented at `saveConfig`.
- **Two files, not one.** The write order makes a half-save fail safe and the read order makes an interleaved read fail safe, but neither is atomic, and the R2 backend has no test coverage for the scheme (deferred above).
- **A corrupted token self-heals rather than refusing.** Anything not matching the stamp shape reads as the sentinel, which a stale draft can also hold. The alternative — 503 forever with no path out — was judged worse.
